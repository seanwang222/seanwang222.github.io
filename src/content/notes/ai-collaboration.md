和 AI 一起写代码，最大的损耗不是它写错，而是它**反复写错同一类东西**。你说过一次「不要用 localStorage 绕过落盘时序」，三天后它又在另一个组件里用了。

原因很简单：约束停留在对话里，而对话不是它每次工作的输入。

## 把约束变成仓库的一部分

`AGENTS.md` 这类文件的作用不是「给 AI 看的文档」，而是**把口头约定固化为可检索的上下文**。里面应该写哪几类东西：

**1. 不可违反的技术底线**

```md
- 落盘唯一入口是 persistence.js，禁止任何组件直接写存储
- 时间字段一律存 UTC ISO 字符串，展示层再转本地时区
- 提交身份固定为 noreply 邮箱，真实邮箱不得进入公开历史
```

**2. 曾经踩过的坑（带结论）**

```md
- 坚果云用 409 表示路径不存在，不是 404（见 docs/architecture/sync.md）
- 应用密码是 16 位随机串，允许 - 和 _，不要用字符集猜
```

这类条目最有价值，因为它们是无法从代码里读出来的**外部事实**。

**3. 界面约束**

```md
- 勾选完成后不得改变行数与行高（避免列表跳动）
- 红色只表示「已逾期」，不表示优先级
```

视觉层面的规则如果只存在设计稿里，AI 是不知道的。

## 约束文件要能被验证

写了规则不等于规则生效。我倾向于把关键约束同时写成断言：

```js
// 防止有人把「测试连接」改回只读已保存配置
assert.ok(source.includes('mergeConfigInput(readCfg(), input)'));
```

文档负责让人理解，断言负责让机器拦住。两者缺一，规则都会慢慢失效。这就是 [[verify-suites]] 里那类「源码断言」的由来。

## 别让它替你做判断

我摸索出的分工是：

| 交给 AI | 自己保留 |
| --- | --- |
| 遍历代码找所有调用点 | 决定哪个是唯一实现 |
| 按 file:line 校对文档 | 判断文档与代码谁对 |
| 补回归用例的骨架 | 决定「什么算正确」 |
| 改写大段重复代码 | 划定边界与例外 |

一旦把「什么算正确」也交出去，你会发现代码越来越像样，但行为越来越不像你要的。

## 副产品：这些文件也是给人看的

`AGENTS.md` 写到最后，新同事（或者三个月后的自己）读完能直接上手。它意外地成了这个项目最有用的文档之一——因为它写的全是「为什么不能那样做」。

写下来的过程本身就是思考。这也是 [[knowledge-garden]] 的起点：**不写下来的判断，等于没有判断。**
