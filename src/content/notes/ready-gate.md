同步类应用最隐蔽的一类丢数据，不是发生在同步中，而是发生在**同步结果还没到位的那几百毫秒里**。

## 现场还原

应用启动后立刻做了三件事：

1. 渲染层从 localStorage 读数据，读到 `{}`；
2. 界面挂载，某个副作用顺手把 `{}` 写回了存储；
3. 主进程从云端下载到真实数据，回填——但磁盘上已经被 `{}` 覆盖过了。

第 2 步的写入不是 bug，它是「初始化默认值」的正常行为。问题在于它发生在一个错误的时机：**数据还没到，但系统已经允许写入**。

## 用一个闸门把时间切成两段

引入一个 `ready` 状态，它是单向的：

```js
let ready = false;          // 回填完成前一律为 false
let queue = [];

function write(data) {
  if (!ready) return;       // 丢弃，不是排队
  persist(data);
}
```

注意这里是**丢弃**而不是排队。排队看起来更「不丢东西」，但实际更危险：积压的写入全是空状态产生的，回填后一次性刷下去，等于用空数据覆盖刚下载的真数据。空状态下的写入没有保留价值，丢掉才是对的。

## applySnapshot 不要通知订阅者

回填函数最容易被写成这样：

```js
function applySnapshot(snapshot) {
  store.set(snapshot);   // 触发订阅者 → 订阅者以为用户改了数据 → 写回存储
  notify();
}
```

订阅者分不清「用户修改」和「系统回填」，于是回填本身触发了一次写盘。正确的做法是回填只改内存、不广播，等 `ready` 置位后界面重新读一次。语义上要区分两条路径：

| 路径 | 是否通知 | 是否落盘 |
| --- | --- | --- |
| 用户修改 | 是 | 是 |
| 系统回填 | 否 | 否 |
| 初次加载默认值 | 是 | 否（未 ready） |

## 退出时的写入是另一条路

`beforeunload` 里不能 await 异步写盘，浏览器不会等你。Electron 里唯一的办法是同步通道：

```js
ipcRenderer.sendSync('flush-sync');
```

主进程收到后用同步 API 落盘。这条路必须存在，否则「改完最后一个字就关窗口」会稳定丢一次数据。这条与 [[atomic-write]] 是配套的：同步写被打断的概率更高，所以更依赖原子替换。
