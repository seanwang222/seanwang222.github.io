这条是实测出来的，不是查文档查出来的。文档说 404 是资源不存在，坚果云偏不。

## 现象

新设备首次同步，`pull` 一直失败，报错「目标已存在或需先创建目录」。用户看到这句话的反应是：我什么都没建，怎么就存在了？

换 `curl` 直接打：

```bash
curl -i -X PROPFIND https://dav.jianguoyun.com/dav/我的坚果云/0_个人/ -u "邮箱:应用密码"
# HTTP/1.1 409 Conflict
```

目录确实不存在，服务端给的是 **409**。

## 为什么 409 会毁掉整条链路

按 RFC 4918，409 的含义是「请求无法完成，因为父集合不存在」。也就是说 409 本身就是一条关于**层级**的信息，不是关于目标的信息。

旧代码把 404 当「云端为空」，于是：

- `pull()` 收到 409 抛异常 → 新设备永远拉不到东西；
- `ensureDir()` 对整个路径只发一次 `MKCOL` → 服务器拒绝（父目录没有），返回 409，代码把它当成「目录已存在」吞掉 → 后续 PUT 全部 404。

两处叠起来的结果是：上传看起来成功了，下载永远 409。数据在云上，但拿不回来。

## 正确的处理

**1. 两个状态码归一为「云端为空」**

```js
const EMPTY_STATUS = new Set([404, 409]);
if (EMPTY_STATUS.has(res.status)) return { empty: true };
```

**2. 逐级创建，每级独立判断**

```js
let acc = '';
for (const seg of segments) {
  acc += '/' + encodeURIComponent(seg);
  const res = await dav('MKCOL', acc);
  if (![201, 200, 405].includes(res.status)) {
    throw new Error(`目录创建失败于层级 ${acc}`);
  }
}
```

201 是新建，405 是「已存在」（Methods Not Allowed），这两个才算成功。409 在这里是错误，必须带出**断在第几层**。

**3. 连接自检要说清缺哪层**

`checkConnection()` 在 404/409 时不要只回一句「目录不存在」，而是逐级 `PROPFIND`，把三层信息一起返回：

- 缺的是哪一级；
- 该级当前实际有哪些子目录；
- 用户配置里填的是什么。

用户改一个格子就能修好，而不是猜。

## 顺带踩到的两个坑

- **路径归一化**：用户从资源管理器复制粘贴，拿到的是 `我的坚果云\0_个人\...`。反斜杠不会被当分隔符，整段被编码成带 `%5C` 的怪名字。归一化只能有一个实现，所有 URL 拼接都要经过它。
- **应用密码不是 16 位字母数字**：坚果云的 16 位应用密码允许 `-` `_`，用 `/^[A-Za-z0-9]{16}$/` 猜字符集会把正确密码判成格式错误。只比长度，别猜字符集。

协议实现里，「按常识写」和「按对端行为写」的差距，往往就是一条永远走不通的同步链路。这条经验后来进了 [[verify-suites]]，用 mock 服务把 409 的语义锁住。
