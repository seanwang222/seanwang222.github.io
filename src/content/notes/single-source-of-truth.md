代码评审里最容易放过的一句话是：「这里先这么写，和那边一样」。问题在于，**「和那边一样」是当下的状态，不是未来的保证。**

## 同一个判断，三个副本

项目里曾经同时存在三份「某天的完成率」：

1. 统计模块里的 `getMonthlyData`：排除未来日，排除不参与统计的日子；
2. 日历组件里的内联计算：不排除未来日，不读排除标记；
3. 图例组件里的硬编码色阶：直接写死了一个十六进制值。

结果是月历和统计卡对同一天给出两个不同的数字，用户看到的是「系统算错了」。实际谁都没算错，只是各算了一遍。

## 修法：留下唯一实现，其余变成调用

```js
// 唯一实现
export function getMonthlyData(items, records, range) { /* ... */ }

// 组件只负责取数与渲染
const days = getMonthlyData(items, records, range);
```

修完之后组件代码通常**变短**，因为重复的分支判断被收走了。这几乎是判定重构方向对不对的一个经验指标：**正确的抽象会让调用方更简单。**

## 颜色也是逻辑

`RATE_COLOR_NONE` 被硬编码进 JSX，看起来只是样式问题。但它是「0% 该长什么样」这个**业务判断**的表达。一旦色阶调整，漏改的那一处就会成为永久的视觉 bug——而且没人会去搜十六进制值。

同理，文案里的常量也该有唯一来源。`APP_PASSWORD_NAME` 定义在主进程，渲染层无法 import，就只能写同名字面量，再补一条断言锁住两边不漂移。

## 怎么发现重复实现

几个搜索习惯：

- 搜同一个错误提示的关键词，出现两次以上就值得看；
- 搜数字字面量：`365`、`92`、`30`、`#6e7681`；
- 看「汇总」类函数里有没有 `filter` 之后再 `filter`；
- 遇到「这里和那边一样」的注释，基本就是分叉前夜。

## 和文档的关系

唯一实现的另一面是：文档里对同一件事也只能有一个说法。如果架构文档说「自动同步只上传」，而代码里有 apply 分支，那不是文档过时，是**系统里存在两个互相矛盾的结论**。

所以 [[electron-docs]] 里每篇末尾都要单列「已知差异」——冲突写出来，比假装一致安全。

相关：[[stats-denominator]] 的分母口径就是被这条原则统一掉的。
