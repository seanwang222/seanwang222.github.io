进程被 kill、机器断电、用户强制关机——写文件这件事在中途被打断是常态，不是异常。问题只在于：被打断之后，磁盘上留下的是什么。

## 结论先写

把数据写成「另一个文件」，再用一次原子的重命名替换目标文件。不要试图用 `writeFile` 直接覆盖。

```js
// 同一卷内的 rename 是原子的：要么看到旧文件，要么看到新文件
await fs.writeFile(tmpPath, json, 'utf8');
await fs.rename(tmpPath, targetPath);
```

重命名之所以敢用来做这件事，是因为它在同一文件系统内不复制数据，只改目录项。目录项替换是一次元数据操作，不会出现「一半是旧内容、一半是新内容」的中间态。

## 为什么直接覆盖会出事

`fs.writeFile` 的语义是「打开、截断、写入」。截断那一刻，原文件就已经没了。如果写在 60% 时进程消失，磁盘上就是一个语法不完整的 JSON。

更麻烦的是读取端怎么理解它。如果读文件的代码写成了：

```js
try {
  return JSON.parse(await fs.readFile(p, 'utf8'));
} catch {
  return null; // 当作「本机没有数据」
}
```

那么「解析失败」会被静默解释成「这台机器是空的」——而空，在同步逻辑里通常意味着「允许用云端覆盖本机」。一次崩溃就变成一次数据清除。

所以 [[ready-gate]] 里那条「回填完成前不写库」和这里的原子写是同一条防线的两段：前者防写得太早，后者防写得不完整。

## .tmp 必须和目标文件同卷

`rename` 跨卷不是重命名，而是「复制 + 删除」，原子性完全消失。临时文件必须放在目标文件同目录下，而不是系统临时目录：

```js
const tmpPath = path.join(path.dirname(targetPath), `.${path.basename(targetPath)}.tmp`);
```

顺带一个细节：临时文件用点号开头，在 Unix 下天然隐藏；Windows 不看这个，所以清理逻辑仍要显式处理遗留的 `.tmp`。

## 遗留的 .tmp 不是垃圾，是证据

启动时如果发现 `.tmp` 还在，说明上次写到一半被打断了。这时正确的做法不是「删掉继续」，而是：

1. 尝试解析 `.tmp`，能解析说明它其实是完整的，可以提升为目标文件；
2. 解析不了就删掉，目标文件本来就还是旧的那份，数据没有丢。

这比「直接把 .tmp 删掉」多花十行代码，但它能把一次可恢复的中断变成零损失。

## 这条规则适用的边界

| 场景 | 需要原子写？ |
| --- | --- |
| 用户数据落盘 | 需要 |
| 配置写入 | 需要，配置损坏等于应用起不来 |
| 缓存 | 不需要，坏了重算即可 |
| 日志追加 | 不需要，`appendFile` 本身够用 |

判断标准只有一个：**这份文件损坏后，是否有人会据此做出错误的决策**。会，就必须原子写。参见 [[local-first]]。
