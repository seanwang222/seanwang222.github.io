一个改动最终能被理解，靠的不是 diff，而是**当时有哪些别的选择，为什么没选**。diff 里看不到被否决的方案，也看不到那条错误的排查路径。

## 一条好提交信息的结构

我现在的写法固定成三段：

```
feat: 一句话说清行为变化

为什么必须改（现象 + 根因），以及上一版错在哪。
- 具体做法 1，以及为什么这样而不是那样
- 具体做法 2
- 回归用例补了什么
```

第一行是给 `git log --oneline` 看的，必须能独立成立。正文是给 `git blame` 之后点进来的人看的。

## 反例与正例

**反例**

```
fix: 修复同步问题
```

三个月后看到这行，唯一能确定的是「有个和同步有关的东西被改过」。

**正例**（节选）

```
fix: 空明文写入不再抹掉应用密码，401 提示带可诊断信息

writeConfig 只在「codec 不可用」分支保留盘上密码，加密可用 + 本次无明文时
会把 passwordEnc 写成空串：一次改自动同步开关或更新 syncedAt 就让应用密码
消失，用户被迫重填、重填时常填成登录密码，之后每次同步都停在 401。
```

读完这段，你知道了：症状（一直 401）、根因（加密可用分支漏了保留）、触发条件（改任意一个设置）、以及为什么用户会填错。这些信息在代码注释里无处安放。

## 为什么值得写这么长

三个具体收益：

1. **排查时间大幅缩短**。下次出现同类 401，直接 `git log --grep=401` 就能找到根因；
2. **阻止重复犯错**。写过一遍「这里为什么不能删」，下次就不会有人（包括 AI）顺手删掉；
3. **逼自己想清楚**。写不出「为什么不是另一种做法」，通常说明还没想透。

## 写长不等于写水

有效的部分只有两类：**根因**和**被否决的方案**。下面这些可以删掉：

- 「优化了代码结构」——没有信息量；
- 逐条复述 diff——diff 自己会说；
- 「根据需求修改」——需求在哪里？

## 和文档的分工

| 载体 | 回答的问题 | 生命周期 |
| --- | --- | --- |
| 提交信息 | 这一次为什么改 | 永久，逐条累积 |
| 架构文档 | 现在整体怎么运转 | 持续更新，会腐烂 |
| 笔记 | 这类问题的一般规律 | 长期，可被复用 |

三者不重复。提交信息是**时间维度**上的记录，架构文档是**结构维度**上的快照。这也是这个站点的「时间线」和「知识空间」分开的原因——见 [[knowledge-garden]]。
