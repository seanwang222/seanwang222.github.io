给一个只有自己维护的项目写架构文档，很容易写成「功能说明书」：这个模块干什么，那个流程怎么走。读起来顺畅，但**无法核对**——因为每一句都没有对应的代码位置。

## 加两个东西就有用了

**1. 每条结论标注 file:line**

```md
ready 闸门在回填完成前丢弃所有写库（storage.js:9-12 与 persistence.js:44）。
applySnapshot 故意不通知订阅者（storage.js:973-979）。
```

行号会过期，这是它的缺点，也是它的价值：**过期是可见的**。读者点过去发现对不上，立刻知道文档需要更新；而一段没有行号的模糊描述，烂了三年也不会有人发现。

**2. 每篇末尾单列「已知差异」**

文档与代码冲突时，以代码为准——但冲突本身必须写下来：

```md
## 已知差异
- README 称「自动同步只做上传」，与 main.js:149-157 的 apply 分支矛盾。
  自动同步是双向的，只是永不带 force。
```

这一节让文档从「声称正确」变成「诚实」。承认不一致比假装一致有用得多，因为前者能驱动修复。

## 写文档时才发现的问题

按代码逐条核对的过程，本身是一次审计。写这三篇的时候顺手记下了三处待修：

- 日历组件自己算了一套每日完成率，与统计模块口径并存；
- 图例颜色是硬编码的十六进制，没有走色阶函数；
- 一个渐变函数在源码里已经没有任何调用点。

这些都不是「写文档时新产生的 bug」，而是**没人读过的地方**。文档的副作用是强迫你把代码读一遍。

## 图表用 Mermaid，边界用 DSL

- 日常阅读用 Mermaid：GitHub 原生渲染，改动成本低；
- 需要严格的组件边界时用 Structurizr DSL：它是模型，不是图片，边界改了图会跟着变。

两者不需要都维护。我的用法是：DSL 只描述边界（谁依赖谁），Mermaid 描述时序。

## 什么时候值得写

判断标准：**这个决定如果不写，半年后会不会被推翻且没人记得原因。**

会，就写。不会，就别写——尤其是「文件目录结构说明」这类熵增最快的部分，让 `ls` 自己去回答。
